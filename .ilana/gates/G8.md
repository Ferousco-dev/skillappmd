## Finding C1 — a metric that was counting the wrong thing

The closure gate's own arithmetic caught a number this project had been quoting since G5.

`334 tests` appears in G5, G6, G7, `docs/audit-report.md`, `docs/test-plan.md`, `docs/scm-plan.md`,
`CHANGELOG.md` and the `TC` counter in `state.json`. It came from the test runner's summary line.
Counted directly, the repository declares **318** test cases — `TC-001` through `TC-318`,
contiguous, no gaps, and every `test()` call in the repository is labelled with one.

Both numbers are real. They measure different things:

- **318** distinct test **cases**
- **344** test **executions**, because contract suites run one case against several adapters —
  `TC-194` runs against SQLite *and* the memory store from a single declaration

The error was reporting an execution count under the label *test cases*, and then deriving test
density from it. Corrected: `MET-005` 334 → **318**, `MET-006` 83 → **79 per KLOC**, and `MET-031`
added to record executions separately so the two can never be conflated again.

**No gate is reopened.** The gate records state what the runner printed on the day and remain
accurate as execution counts; the historical records are left unedited rather than backdated. No
verdict at any gate turned on the difference between case count and execution count — every criterion that used the
figure required *all* tests to pass, which they did and do.

**What it says about the process.** The `TC` counter was maintained by hand, from a number the
runner produced, and no instrument checked it against the ids actually assigned. Requirements had a
traceability checker; test-case identity did not. This is the same failure shape as the G7 finding —
*a count nobody verified* — and it went eight gates without being noticed, including one gate
whose entire job was auditing quality.

The honest reading is that the closure gate earned its place on this run. Criterion 8 is marked
**qualified** for the related reason: `ONBOARDING.md` has not been run past an actual newcomer, so
its central claim — that a stranger could operate this from the docs — is at present untested. It
is written down as a claim, not as a verified fact.

## The closing number

```
findings from review, before any code ran            8
defects found during construction (before G5)        7
defects found at verification (G5)                   1
defects found after release                          0

prevention ratio  (7 + 8) / (7 + 8 + 1)  =  93.8%
defects escaping to verification           1 / 8  =  12.5%
```

**The zero on the fourth line proves nothing.** Nothing is deployed and nothing has users. It is
recorded as a baseline slot, not as an achievement, and it is the number most likely to be wrong.

The honest denominator problem: a prevention ratio counts defects *found*. It cannot count defects
still present. `DEF-006` — a duplicate that never settled and hung the whole suite — passed every
existing test for several increments. Its absence from the count until increment 9 is precisely
what the metric cannot see.

**Baseline for the next run:**

| Metric | This run | Next-run target |
| --- | --- | --- |
| Prevention ratio | 93.8% | ≥ 90% at a larger defect count |
| Gate first-pass rate | 60% (2 failures: G1, G4) | ≥ 70% |
| Mean defect escape | 2.9 increments | ≤ 2.0 |
| Mandatory requirement coverage | 100% | 100% — non-negotiable |
| Review yield before execution | 8 findings | maintain — this is the cheapest yield in the run |

A rising prevention ratio at a *falling* defect count means nothing is being found, not that
nothing is there. If both drop together next run, `DOCTOR` mode is due.

## The change carried forward

**One**, per Article 15.

**`subsystem-coverage.js`** — verifies that every subsystem named in `ARCHITECTURE.md` §5 is
assigned to a real increment in `ROADMAP.md`.

- **Owner:** `[planner]` · **Starts:** next run, at G2, before any increment is written
- **Metric:** unassigned subsystems at G2 — target **0**
- **Why this one:** both gate failures on this run (G1 and G4) traced to the same cause — *a plan
  that lost a subsystem the design had specified*. `DEF-008` was an entire connector, `REQ-004`,
  designed and then absent from every increment.
- **Why it is credible:** it is executable, it is in CI, and its first honest run found live drift —
  increments 11 and 12 had been built but were never written into `ROADMAP.md`. Its first fuzzy
  version produced false positives; making the mapping explicit (an Increment column in
  `ARCHITECTURE.md` §5) was the fix. **It fails the build when an assignment is removed** — verified,
  not assumed.

The checker is itself under test. `TC-315`–`TC-318` prove it passes a clean plan, **fails** on a
subsystem with no increment, **fails** on an increment that does not exist, and passes against this
repository. Mutation-checked: deleting the `process.exitCode = 1` line turns two of the four red. A
checker whose failure path is untested is a checker that only ever passes.

C1 argues for a second instrument — a `TC` id checker. It is **not** adopted, because Article 15
says one change, and adopting two is how process changes stop being real. It is recorded in
`docs/retrospective.md` as the first candidate for the run after next.
