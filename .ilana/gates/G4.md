## §A — Why this gate FAILS

**`REQ-029`–`REQ-034`: the RAW storage layer was never built.** The `ObjectStore` port is defined
in `packages/ports/` and **has no adapter**. `raw_object_key` is a column that is always null.

This was not a decision. It was an omission, and the gate exists to find exactly this.

| Requirement | Status |
| --- | --- |
| `REQ-029` raw content stored immutably, addressed by hash | **ABSENT** |
| `REQ-030` raw record retains bytes, source, URL, timestamp, version, hash | **ABSENT** |
| `REQ-031` RAW → PARSED → CANONICAL are distinct layers | **ABSENT** |
| `REQ-032` reprocess stored raw **without re-contacting the source** | **ABSENT** |
| `REQ-033` raw is internal processing data behind access control | **ABSENT** |
| `REQ-034` retention rule, deletable, deletion recorded | **PARTIAL** — tombstones exist; there are no bytes to delete |
| `REQ-052` rebuild a derived index from canonical | **ABSENT** — `rebuildReport()` is accounting, not a rebuild |

### What this actually costs

- **`REQ-032` is the load-bearing one.** BRIEF §10's whole argument — *"if our AI model improves
  six months later, reprocess old raw data without crawling the source again"* — does not hold.
  `REQ-095` re-analysis correctly *identifies* affected records, and then has nothing to reprocess
  from. The corpus JSONL happens to contain content, but that is the **corpus**, not our raw layer,
  and it exists only because increment 9b extracted it.
- **`DEC-019` rights-aware retention has nothing to retain.** The 90-of-131 `process-then-delete`
  postures measured in increment 7 govern bytes that were never stored.
- **`REQ-052` was claimed as designed and is not implemented.** `NFR-010`'s "delete every derived
  index and rebuild" has never been executed.

### The signal I had and did not chase

Increment 10's removal demo printed `bytes deleted false — no object store configured`. I noted it
as correct behaviour for a null port and moved on. It was correct behaviour, and it was also the
system telling me a whole layer was missing. **A graceful degradation that nobody questions is how
an absent subsystem stays invisible.**

`ROADMAP.md` §2 is the root cause: increment 2 was written as "canonical store + backup" and raw
storage was never given an increment of its own. It appears in `ARCHITECTURE.md` §5 as a Phase 1
subsystem (✅) and in `INGESTION.md` §5, so the design was right; the plan lost it.

## §D — `DEC-027` portability proof: **PASSED**

`DATABASE.md` §8 set the falsifiable test: *a second adapter can be written and the full suite pass
without editing `skill-core/` or `ingestion/`.*

Built `MemoryCanonicalStore` — **plain JavaScript maps, zero SQL statements**. One contract suite,
**27/27 passing against both adapters**, and `git status` confirms `skill-core` and `ingestion`
**unmodified**.

**A Postgres adapter would have proved less.** Postgres and SQLite share SQL, so a port that leaked
SQL would still have passed. This pair shares nothing but the interface — which is the property
actually under test.

`TC-207` is the sharpest result: **a SQL store and a plain-map store produce the same canonical
digest, byte for byte.** The port carries no engine semantics.

The suite also caught a real divergence: the memory adapter validated cursors **lazily inside a
`findIndex` callback**, so an empty store never validated at all and a malformed cursor silently
became a garbage sort key. Fixed to eager validation in both. A same-family adapter pair would
never have surfaced it.

## Decision

**G4 FAILS.** Not on quality of what exists — on **completeness of what was built**. Raw storage is
a Phase 1 subsystem named in the brief (§10), the SRS (`REQ-029`–`034`), and the architecture
(`ARCHITECTURE.md` §5), and it is absent.

**Remediation: increment 11** — `ObjectStore` port adapters (`fs` local, `r2` shape), raw-write in
the pipeline, rights-aware retention wired to real bytes, and index rebuild. Then G4 attempt 2.

**Overrides:** none. Reporting a failure the gate found, per Article 2.
