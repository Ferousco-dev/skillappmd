## §C — `DEF-007`, found by re-running existing evidence

Wiring the derived index inline pushed the ladder to **128 MB, over budget**. Every unit test
passed; only the increment 9b ladder — which nothing forced me to re-run — showed it.

I first removed a redundant `getCanonical()` re-read. **It was not the cause** (128 → 131 MB), and
recording that matters: stopping at the plausible fix would have left the real problem in place.
The real cause was coupling indexing to the canonical write at all, which `DATABASE.md` §46 had
already ruled out. Indexing moved off the ingest path; `rebuildSearchIndex()` is now the single
mechanism, which is also the recovery path.

**119 MB, within budget.** Headroom is genuinely smaller than the pre-increment 85 MB — that is the
`raw_objects` rows, and it is stated rather than glossed.

Also caught, in my own verification script rather than shipped code: a check over the first 150
extracted rows concluded "search works: false". Those are stratum 0 — ~10-byte files with no
frontmatter — so zero hits was correct. **The head-sampling error `DEC-024` exists to prevent,
walked into again.** Re-run with a stride: 240 records, 79 named, search returns hits.
